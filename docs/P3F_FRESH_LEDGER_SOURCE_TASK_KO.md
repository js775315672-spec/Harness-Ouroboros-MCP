# P3f — 신규 실소스 과제: 개발 증거 대장 문자열 입력 검증

## 2026-11-16 별도 사전등록 실험 목적
P3a/P3b의 sandbox_policy 보안 과제는 두 모델 호출 모두 무변경 답안을 반환해 0/2 합격이었다. P3f는 다른 실제 저장소 모듈 **scripts/development_ledger.py:validate(records)**의 신규 결함을 대상으로 모델의 독립 코드 수정 능력을 실험한다. 이전 P3a/P3b 출력은 새 프롬프트에 제공하지 않는다.

## 실제 기존 소스의 결함
개발 증거 대장은 record.change와 record.fixes[]를 비어있지 않은 문자열인지 등만 검사한다. 제어문자(NUL, ESC, 개행) 및 비현실적으로 큰 문자열과 지나치게 긴 수정 목록을 그대로 받아 이후 로그·에이전트 피드백의 무결성을 해칠 수 있다. 기존 CI URL·40자리 commit·통과된 검사·연속 사이클 확인은 그대로 유지해야 한다.

## 이번 처음 보는 고정 과제
- 기존 validate() 함수 전체만 Qwen 7B가 직접 재작성. 나머지 import, 전역변수, 다른 함수/파일은 수정 불가.
- 변경 설명은 UTF-8 256바이트 이내, 적절한 문자열, control ord<32/127..159 거부.
- fixes는 최대 12개, 각 항목은 1~128 UTF-8바이트의 문자열이며 동일 제어문자 거부.
- 기존 회귀 15개(test_development_ledger.py 8 + test_ci_attestation.py 7) 및 신규 보안 홀드아웃 10개, **합계 25개**를 처음부터 고정.
- 모델은 원래 함수 소스+문제 계약만 보며 숨겨진 10개 테스트 파일 내용을 보지 못한다.
- 기준선 기존 코드에서 기존 15개 통과, 신규 보안 10개 중 하나 이상 실패(negative control) 필수.
- 새 Qwen CPU 추론 **딱 1회**, raw 원본 응답 SHA-256 + original source SHA + test SHA + unified diff SHA 보관.
- 모델 코드는 보안 AST 검사 후 단일 함수 구간에만 적용하고, 읽기전용·네트워크 차단·비루트 Docker에서 25개 테스트 실행.
- 별도의 독립 GitHub 러너가 원본 모델 응답/소스/테스트를 다시 검사하고, 모든 조건이 통과해야 **candidate_acceptance_gate** 초록색. 모델이 실패하면 해당 워크플로 빨간색 유지.

## 검증된 빌드 1회 재사용
같은 실행에서 먼저 P3e 방식의 pinned llama.cpp를 **한 번** 컴파일하고 SHA-256 및 정확한 소스 commit을 포함한 GitHub Actions artifact를 업로드한다. 모델 작업은 그 동일 run의 바이너리만 다운로드해 출처와 체크섬을 검증한 후 실행한다. GitHub Actions 외부 바이너리 캐시는 사용하지 않으며 GGUF 공식 모델 다운로드/해시 검증은 별도로 지속한다.

## 성공 의미의 경계
- model-only pass 25/25 + 독립 재생: 해당 실제 소스 함수의 제한된 성공을 의미. 범용 에이전트 성능·8×8 자기진화·GitHub 소스 패치 커밋을 증명하지 않음.
- candidate acceptance가 빨간색이면 모델 단독 소스 수정 실패. Harness가 초록색이어도 둘을 혼동하지 않음.
- 성공 후보를 실제 저장소 파일에 반영하려면 그 모델 원본 출력의 출처/라이선스/안전성 검토 후 **별도 Draft PR에서 동일 원본 소스 변형을 커밋하고 정확한 SHA CI**까지 다시 검증해야 함.
- 이전 연구 PR 및 기존 평가 테스트를 모델에 맞춰 변경하지 않는다.
- 비밀키·유료 API·자동 병합·무인 재귀 작업·실제 매매·GitHub write 권한은 사용하지 않는다.
