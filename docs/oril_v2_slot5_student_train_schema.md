# ORIL v2 slot 5 — student training row schema boundary

## Reproduction and hypothesis

PR #286's pinned consumer checks the marker and hashes, but its previous training row parser accepted **any JSON object with a list-valued messages field**, including an attacker-supplied `split: heldout` or system/tool roles. The marker is generated by a local producer and proves consistency, not that data is suitable for training.

**Hypothesis:** exact two-turn `user → assistant` rows and bounded optional metadata can reject malformed training instructions while preserving all legitimate curator outputs. Falsifiable by adversarial cases and regression suites.

## Scope

- Validate every row *after* descriptor-pinned SHA verification and *before* returning immutable bytes to the caller.
- Reject unexpected top-level keys (including `split`, `heldout`), extra system/tool roles, non-string/empty/oversized answers, ambiguous metadata, duplicate case IDs, invalid quality.
- Preserve the legitimate curator schema `messages + metadata` and older minimal `messages` fixtures.
- **Does not inspect semantic content** for sensitive information, prove teacher review authenticity, attest GPU execution, or execute a student model. A user message containing a secret is still possible and requires an independent privacy/provenance gate.

## Acceptance and handoff

Run `python3 -m unittest discover -s tests -p 'test_oril_v2_distill_student_train_schema.py' -v` and existing pinned consumer, pair marker, teacher curation tests on the **exact head SHA**. Require all green, zero skips. The CI is independent runner execution of developer-authored tests, **not independent hidden evaluation**.

Next cycle: require signed/frozen external provenance of teacher examples, privacy and content policy checks before training, and actual student inference on >=30 independent heldout groups. Only claim LoRA after actual GPU logs, adapter bytes/SHA, and separate evaluator evidence. Do not modify protected gates or deploy.
